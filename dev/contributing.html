Contributing#

TimeToShare! is schema-first. The current schema, 0.2.0, is the contract; the Python and TypeScript packages validate it, and timetoalign emits its fixtures.

Schema changes#

A version’s schema is three documents in schema/<version>/: the manifest schema timetoshare.schema.json, the provenance schema provenance.schema.json and the column types of the tables, tables.json, each with the $id https://timetoalign.github.io/timetoshare/<version>/<file>. A release serves them, with the catalogue’s schema catalogue/catalogue.schema.json as <version>/catalogue.schema.json, at their $ids and at https://timetoalign.github.io/TimeToShare/<version>/<file> on this repository’s own GitHub Pages site; python3 scripts/check_published.py checks that every $id is the address its document is served at and that every reference names a served document. An unreleased version is changed in place; a released one is never altered. A new version replaces the current one in schema/: the repository and both packages hold the current version only, with no migrations, and a replaced version lives in the git history at its tag, in its released packages and on the project site. Update the version declarations in both packages, add shared rejection and warning cases, regenerate js/src/generated/ with pnpm generate, and re-emit the fixtures through timetoalign.

The manifests under fixtures/<version>/ and its groups/, bundles/ and statements/ subdirectories are generated artifacts in canonical YAML, each in the complete form beside its minimal twin. Use an environment containing the timetoalign revision represented by the schema:

python scripts/emit_fixtures.py --timetoalign-commit "$(git -C /path/to/timetoalign rev-parse --short HEAD)"

Do not edit a fixture by hand. The script refuses to write into the fixtures of a version whose v<version> tag exists. The manifests of flow control under fixtures/<version>/flow/ are emitted by the same script (scripts/fixtures/flow.py); fixtures/flows/<version>/ holds their expected flows, derived by hand, each beside its trace. A manifest whose flow control is written in the earlier form (the key type with jump_from, jump_to or flow_marker, one of those words as its role, or target without role) is converted with python scripts/convert_flow_control.py <file>…, which the validators’ refusal names. Rejection cases under fixtures/rejections/ and warning cases under fixtures/warnings/ are authored by hand and written with dumps. The serialization cases under fixtures/serializations/ are derived by hand from the README’s “Serializations” alone, in the layout its “Fixtures” section prescribes (cases/, readings/, refusals/ and refusals-writing/); a change to a serialization rule changes the README and these cases together, and both packages then reproduce them byte for byte. Their bytes, carriage returns included, are significant: .gitattributes marks fixtures/serializations/** -text, so git never converts their line ends.

The drawing specification#

docs/drawing.md specifies the graphical object, arithmetic, default styles, font, layout, SVG and TikZ writers, and the block that draws every manifest with its frames, cards, bands and ancestor lines. A drawing is derived and has no schema or exchanged JSON form. The specification pins the drawing. A rule a reader could not reproduce from the specification alone is a defect of the specification.

The drawing uses fonts/DejaVuSans.ttf from DejaVu Sans 2.37 and, for every code point DejaVu Sans does not map and Noto Music does, fonts/NotoMusic-Regular.ttf from Noto Music 2.004. fonts/DejaVuSans-LICENSE and fonts/NotoMusic-LICENSE contain their licences, and fonts/dejavu-sans-2.37+noto-music-2.004.metrics.json contains the advance widths of both used to measure text. Regenerate the metrics from python/ with:

uv run python ../scripts/extract_font_metrics.py

Python exposes the files through FONT_FILES and font_paths() and the metrics through font_metrics(). The npm package exports FONT_FILES, fontMetrics and the @timetoalign/timetoshare/fonts/* subpath.

Dependencies and decisions#

Add a dependency only with a numbered MADR in decisions/. The record must assess writing the component here and its long-term maintenance cost, name the audited version, and set a review date. Do not add speculative dependencies or options.

Package manifests declare compatible version ranges because published packages resolve in consumers’ environments. The lockfiles, python/uv.lock and js/pnpm-lock.yaml, pin exact versions. An audited dependency release must have been available for at least 14 days before it is added.

Tests#

Tests are README-first. Update the relevant python/tests/README.md or js/tests/README.md to state the proof required, then write tests with exact expected values.

Run the complete local checks:

cd python
uv sync
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv build

cd js
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm generate
pnpm build

From the repository root:

python3 scripts/check_versions.py

Known limitations#

  • The validator tests do not pin the JSON implementation’s maximum safe-integer boundary in either implementation.

  • Python and TypeScript rejection paths are independently compared with expected values, but no test compares both implementations’ paths for the same generated invalid manifests.

Release#

Releases are made by release-please and .github/workflows/release.yml. Write commit messages in the Conventional Commits form; release-please builds CHANGELOG.md from them.

A TimeToShare version is a schema version, so release-please does not compute it from the commits. The commit that adds a schema version updates every declaration (python/pyproject.toml, js/package.json, SCHEMA_VERSION in python/src/timetoshare/validate.py and js/src/validate.ts, and the self entry in python/uv.lock), holds the documents of schema/X.Y.Z/, a non-empty fixtures/X.Y.Z/ with its drawings/, and the rejection and warning cases, and passes python3 scripts/check_versions.py. The commit carries the footer:

Release-As: X.Y.Z

On every push to main, release-please opens or updates a release pull request with that version and its changelog entry. Merging the pull request tags vX.Y.Z and creates the GitHub release. The release job fails when the version differs from the declarations, and the publish job checks the tag again before publishing. It then runs the Python and JavaScript checks, builds both packages, and publishes them through OIDC trusted publishing. Do not push version tags by hand. When publishing fails part-way, run the Release workflow by hand from the Actions tab with the release tag (v0.1.0) as its input: it publishes that release again, skipping every file a registry already holds, and serves its documents again.

The workflow then publishes the documents of every released tag at two addresses, each set assembled from the tag by scripts/check_published.py, which refuses a tag whose documents name an address not served. The pages job deploys this repository’s own site, https://timetoalign.github.io/TimeToShare/, which holds <version>/<file> for every document of every released version. A second job adds the released version’s documents to timetoshare/<version>/ in the organisation’s site repository, TimeToAlign/timetoalign.github.io, where each is served at its $id, https://timetoalign.github.io/timetoshare/<version>/<file>. GitHub Pages paths are case-sensitive, so the two addresses are two copies of one file.

The workflow needs the repository to be public (npm provenance and the public schema site require it), GitHub Actions to be allowed to create pull requests in this repository, GitHub Pages enabled with GitHub Actions as its source before the first release pull request is merged, the secret ORG_SITE_DEPLOY_KEY, the private half of a deploy key with write access to TimeToAlign/timetoalign.github.io, and a trusted publisher on each registry:
